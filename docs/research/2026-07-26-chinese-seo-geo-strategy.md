# wechat-notebank 中文 SEO / GEO 策略重思考

> 状态：策略建议，尚未授权实施 · 日期：2026-07-26 · 范围：GitHub About、README、公开文档与未来独立站；不修改产品行为

## 结论

GitHub About 应改成**中文优先、英文补充**，不建议只保留英文，也不建议彻底删除英文。

推荐文案：

> 微信公众号文章转 Markdown：本地归档到 Obsidian、Logseq 和个人知识库 | Archive WeChat articles as local Markdown.

理由不是“产品来自中文语境，所以所有文字都要中文化”，而是：

1. 核心用户的需求表达是“公众号文章保存”“微信文章转 Markdown”“导入 Obsidian”“本地知识库”，当前 About 没有承接这些中文语言。
2. 仓库名、CLI、生态工具名和 GitHub Topics 仍以英文为主，保留一句英文可以继续解释项目类别并承接英文检索。
3. 当前 README 首屏已经中文优先，About 纯英文造成了入口语义不一致。
4. 产品已经从单纯归档发展到“归档、Agent 加工、人工审核、发布为可追溯知识资产”。About 应继续用具体的归档任务获客，同时指向本地知识库这一最终结果；更深的差异留给 README 和专题页解释。

更关键的是，GitHub 默认仓库搜索主要检索仓库名、Description 和 Topics；README 内容需要用户显式使用 `in:readme` 才进入搜索范围。因此，中文只写在 README 里不能替代中文 About。[GitHub 仓库搜索官方文档](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories)

本轮策略的核心不是继续堆关键词，而是建立三层可发现性：

- **搜索入口**：让中文用户用真实任务语言找到项目。
- **答案入口**：让搜索引擎和 AI 能直接抽取清晰、稳定、有边界的产品事实。
- **采用入口**：让用户从搜索结果进入后，能快速判断“适不适合我”并完成第一次安装。

## 为什么需要重新思考

2026-07-12 的 [JTBD、SEO 与 GEO 设计](../superpowers/specs/2026-07-12-jtbd-seo-geo-design.md) 已经完成了第一轮基础建设：

- README 首屏改为中文价值主张，并保留英文摘要；
- package description 和 keywords 补齐英文搜索语义；
- GitHub About 与 Topics 完成英文技术语义配置；
- Agent Skill 补齐自然语言触发边界。

这一轮工作是有效的，但主要解决“仓库是否具备基本可描述性”。现在暴露出的下一层问题是：

- 用户是中文用户，GitHub About 却仍然完全用英文表达；
- README 很完整，但 581 行内容同时承担定位、安装、命令手册、知识加工协议和故障排查，首访者与机器都需要从大量信息中判断重点；
- 当前公开页面只有 GitHub 仓库，无法自主配置 sitemap、结构化数据、搜索站长工具和 crawler 策略；
- “GEO”在上一轮主要等同于 Skill 触发优化，还没有覆盖公共网络上的 AI 引用与答案可见性；
- 2026-07-26 对“微信公众号文章转 Markdown”“公众号文章归档 Obsidian”“微信文章本地知识库”等查询的抽样未看到本仓库出现在返回结果中。这只是一次非个性化抽样，不能当作稳定排名结论，但足以说明“页面包含关键词”尚未形成可验证的搜索存在感。

因此，本次不是推翻上一轮，而是从“元数据优化”升级为“中文用户发现与可信答案体系”。

## 当前状态审计

### 已经做对的部分

- README 第一屏已经直接表达“微信公众号文章转本地 Markdown、进入 Obsidian / Logseq / 个人知识库”。
- 一句英文摘要保留了 `WeChat Official Account`、`Markdown`、`Obsidian`、`Logseq` 等跨语言实体。
- README 已明确本地运行、不上传知识库、保存原文不依赖大模型，这是重要的信任差异。
- package metadata 与 GitHub Topics 已覆盖主要英文类别词。
- Agent Skill 已覆盖归档、批量导入、加工、审核、撤销等真实任务语义。
- 仓库已经有 Release、公开使用说明、测试和清晰边界，不是只有概念说明的展示项目。

### 当前缺口

1. **About 语言与用户语言错位**
   About 是 GitHub 列表、仓库页右栏和外部摘要的重要短文本，但目前只表达英文归档场景。

2. **产品定位发生了变化，短描述没有同步**
   当前产品差异不只是“把网页转成 Markdown”，还包括本地优先、Agent 操作、候选内容先审核再发布、知识资产可追溯。短描述无需塞入所有能力，但至少应体现“本地知识沉淀”这一结果。

3. **根 README 信息密度过高**
   首屏定位清楚，后半部分同时承载大量内部协议和高级命令。它更像完整手册，还不是清晰的“发现页 + 快速采用页”。

4. **没有自有搜索资产**
   GitHub 页面可以被公开访问，但仓库维护者不能控制其技术 SEO、crawler 策略、结构化数据或站长工具验证。只依赖 GitHub，会限制后续 SEO 与 GEO 的可测量性。

5. **搜索意图与页面结构尚未一一对应**
   “微信文章转 Markdown”“公众号文章导入 Obsidian”“批量保存公众号文章”“公众号文章失效前备份”目前都汇总在同一 README 中，没有稳定的专题答案页。

6. **缺少 GEO 基线**
   目前没有固定问题集去测试 ChatGPT、Perplexity、Gemini、Copilot 等是否会提及项目、是否给出正确链接、是否准确描述边界。

## 定位策略

### 一句话定位

面向用户的主定位：

> 把微信公众号文章保存为自己掌控的本地 Markdown，并在人工审核后沉淀为可追溯的知识资产。

搜索入口定位：

> 微信公众号文章转 Markdown / Obsidian 的本地归档工具。

英文类别定位：

> Local-first WeChat article archiver for Markdown knowledge bases.

三句话承担不同职责，不应强行压成一句充满关键词的口号：

- 主定位解释用户获得的进步；
- 搜索定位承接明确任务；
- 英文定位帮助 GitHub 和国际用户快速归类。

### 竞争心智

搜索结果里常见的是在线“微信文章转 Markdown”转换器。本项目不应只在“转换格式”上竞争，而应明确自己的差异：

- 文件与知识库由用户自己掌控；
- 单篇与 Excel 批量归档；
- 保留来源元数据；
- 可在 Agent 中操作；
- 内容加工先生成候选，人工批准后才进入正式知识库；
- 不把“已经失效的文章恢复”“自动读取微信收藏夹”等未实现能力写入定位。

因此，获客词可以是“转 Markdown”，真正的产品差异应落在“本地优先、可追溯、人工审核的知识沉淀”。

## 语言架构

### GitHub About

采用中文在前、英文在后的单段短描述。

推荐：

> 微信公众号文章转 Markdown：本地归档到 Obsidian、Logseq 和个人知识库 | Archive WeChat articles as local Markdown.

备选，更偏产品差异：

> 把微信公众号文章保存为本地 Markdown，并经人工审核沉淀到 Obsidian、Logseq 或个人知识库。Local-first WeChat article archiver.

推荐第一版，因为它直接承接中文任务查询，而且没有把可选的知识加工写成每次归档的必经步骤。第二版能表达产品差异，更适合未来首页的定位段落。

### GitHub Topics

Topics 继续使用英文 slug，不把“中文化”等同于把所有 Topics 翻译成中文。建议优先保留与任务直接相关的词，减少宽泛的实现词。

当前核心 Topics 已经合理，建议先保留：

`wechat`、`wechat-article`、`wechat-official-account`、`markdown`、`obsidian`、`logseq`、`knowledge-base`、`article-archiver`、`local-first`、`cli`、`typescript`、`personal-knowledge-management`

不为占满额度继续堆词。只有固定 GitHub 查询基线显示确切缺口时，再测试 `wechat-markdown` 或 `wechat-archive`；若 Topics 需要收缩，优先评估 `typescript`、`cli` 这类通用技术词。

### README

继续中文为主，不建议把根 README 改成中英逐段对照。逐段双语会显著增加长度，也会削弱中文用户的阅读效率。

建议结构：

1. H1 保留稳定的产品实体 `wechat-notebank`，不要为了关键词频繁改名。
2. H1 后的第一句明确写出“微信公众号文章转 Markdown 与本地知识库归档”，并保留英文类别摘要。
3. 第一屏保留最短命令、隐私承诺和效果图。
4. 在安装前增加“它和在线转换器有什么不同”，用真实差异帮助用户决策。
5. 把高级 pack 协议、完整命令字典和长故障排查迁到独立 docs，README 保留摘要与链接。
6. 如英文用户开始形成真实采用，再增加 `README.en.md`；当前不把全量英文翻译列为 P0。

## SEO 路线

### P0：先修 GitHub 入口

目标是用最低成本让现有公开入口与中文用户语言一致。

- 更新 About 为中文优先、英文补充；
- 更新 Social preview，使中文价值主张在分享卡片中可见；
- 保留 H1 的稳定产品名，在 README 第一屏明确“微信公众号文章转 Markdown”；
- 在 README 首屏集中说明项目名、推荐命令、兼容命令和中文展示名之间的关系；
- 把泛化的截图 alt 改成“归档后的文件夹结构”“微信公众号文章转 Markdown 效果”等真实描述；
- 增加“与在线转换器的区别”和 3 至 5 个任务型 FAQ；
- 保留现有 Topics，先建立固定查询基线，不为关键词数量继续扩充；
- Release 描述统一使用同一定位，并清楚写出支持平台和安装边界。

### P1：建立可控的中文入口站

如果目标只是维护一个 GitHub 项目，P0 已足够；如果目标是持续获得中文自然搜索和 AI 引用，则需要独立公开站点。

建议先用 GitHub Pages 或轻量静态站建立：

- 首页：核心定位、效果、隐私差异、快速安装；
- `/wechat-to-markdown/`：微信公众号文章转 Markdown；
- `/wechat-to-obsidian/`：保存到 Obsidian / Logseq；
- `/batch-import/`：Excel / Numbers 批量归档；
- `/agent-workflow/`：Codex / Claude Code 操作与人工审核；
- `/privacy-and-boundaries/`：本地运行、数据边界、版权与能力边界；
- `/faq/`：真实任务问题的短答案。

站点上线时再配置 title、description、canonical、sitemap、robots、Open Graph、站长工具验证和基础结构化数据。不要在没有页面体系时先做一堆标签工程。

### P2：建立真实外部信号

SEO 与 GEO 都不能只靠自己页面上的自我描述。后续内容与发布应围绕真实案例和可复现证据：

- 一篇完整的中文发布说明，演示从公众号链接到本地 Markdown；
- 一篇与在线转换器的边界对比，避免贬低竞品，只比较数据位置、批量能力、元数据和审核流程；
- 一个可公开的示例知识库，不包含受版权保护的第三方文章正文；
- 在相关社区获得真实使用者的教程、讨论、Issue 或引用；
- 每个 Release 保持稳定说明、校验文件和兼容边界。

## GEO 路线

这里把 GEO 定义为：当用户向生成式搜索或通用 AI 询问“如何保存公众号文章到 Markdown / Obsidian”时，项目更容易被发现、正确理解并作为来源引用。

### 高确定性动作

这些动作符合搜索与 AI 平台公开的抓取、索引和引用机制：

- 保持关键页面公开、可抓取，并使用稳定 URL；
- 用完整句子明确回答“是什么、适合谁、怎么做、不能做什么”；
- 产品名、仓库名、CLI 名、Skill 名和一句话定位保持一致；
- 把版本、系统要求、安装来源、隐私边界写成可引用事实；
- 用 HTML 文本承载关键事实，不把核心解释只放在图片里；
- 为每个重要任务提供独立页面和直接答案；
- 使用真实示例、测试、Release 与公共采用证据支撑产品声明；
- 在自有站点按目标决定是否允许各平台的搜索 crawler 与训练 crawler，而不是把两者混为一谈。

### 可验证但非排名保证的实验

可以做，但不应承诺它们会直接提高 AI 引用：

- `SoftwareApplication` 等结构化数据；
- 面向任务的 FAQ 与 How-to 页面；
- 标准化的 Markdown / HTML 双版本文档；
- 在首页提供简洁的“给 Agent 的安装提示词”。

这些更像降低机器理解成本的实验项，需要用引用测试验证，不应当作确定的排名因子。

`llms.txt`、固定字数分块和所谓“特殊 GEO schema”当前没有主流平台的排名承诺；Google 还明确表示 AI 搜索不需要额外 AI 文本文件或特殊 schema。它们默认不进入近期路线，只有在基础抓取、索引和内容完成后，才值得做低成本对照实验。

### 不建议投入

- 为每个近义词批量生成低价值页面；
- 隐藏关键词、重复堆叠中英文关键词；
- 在没有证据时宣称“专为 ChatGPT / Perplexity 优化”；
- 把 crawler 全部放开当成 GEO 成功；
- 把 AI 是否提及项目当作唯一成功指标；
- 为追求曝光弱化版权、访问权限和本地隐私边界。

## 衡量体系

### 发现

- 自有站点在 Google Search Console / Bing Webmaster Tools 的展示量、点击量、查询词和已索引页；
- GitHub Traffic 的来源、独立访客、clone 与 Release 下载趋势；
- 核心中文任务词是否开始出现站点或仓库页面；
- 外部教程、社区讨论和自然引用数量。

### 理解

- 首访用户能否在 30 秒内回答：它是什么、与在线转换器有什么不同、数据去了哪里、是否适合自己的系统；
- 搜索摘要和 AI 回答是否准确表达本地运行、Markdown、Obsidian / Logseq、人工审核和能力边界；
- AI 是否错误宣称能恢复失效文章、读取微信收藏夹或自动发布未经审核内容。

### 采用

- README / 官网到固定 Release 的点击；
- Release 下载与真实验证用户的首次成功安装；
- `doctor --json` 成功完成的自愿反馈；
- 从第一次归档到再次使用的公共采用证据。

项目坚持不收集用户知识库和文章正文，因此不应为了增长指标引入侵入式遥测。采用层继续使用当前 `CONTEXT.md` 定义的公共采用验证方法。

### GEO 基线问题集

每月用固定问题集在主要生成式搜索产品中抽样，记录“是否出现、是否链接、描述是否准确”，不要只记录排名：

1. 有什么工具可以把微信公众号文章保存成 Markdown？
2. 怎么把公众号文章导入 Obsidian？
3. 如何批量归档 Excel 里的公众号文章链接？
4. 有没有本地运行、不上传知识库的微信文章归档工具？
5. 能否用 Codex 或 Claude Code 整理公众号文章？

结果只能作为抽样，因为模型、地区、账号与时间都会影响回答。

## 优先级与决策门

### 第一阶段：GitHub 中文入口，预计 0.5 至 1 天

产出：About、Topics、Social preview、README 第一屏与 FAQ 的小范围调整。

验收：中文与英文定位一致；无关键词堆叠；未写入未实现能力；不改变产品行为。

### 第二阶段：中文入口站，开发预计 3 至 5 天，首轮观察至少 8 至 12 周

启动条件：确认项目希望持续获得 GitHub 之外的自然搜索与 AI 引用。

产出：轻量静态站、5 至 7 个核心页面、搜索站长工具与索引基线。

验收：每个页面对应一种真实任务意图；可抓取；可测量；与 README 不产生版本冲突。

### 第三阶段：内容与分发，持续进行

启动条件：已有稳定首页和版本化文档。

产出：真实案例、发布说明、公开示例、社区引用与月度 SEO / GEO 复盘。

验收：新增内容必须回答真实问题或提供新证据，不为关键词数量生产页面。

## 下一步规划前需要确认的三个决策

1. **主获客定位**
   推荐继续用“微信公众号文章转 Markdown / 本地归档”获客，用“人工审核的可追溯知识资产”形成差异。不要用抽象的“AI 知识加工”取代用户已经会搜索的任务语言。

2. **是否建设独立站**
   推荐分阶段：先完成 GitHub P0；确认要长期做自然增长后，再建设轻量独立站。没有独立站，很难真正测量与控制 SEO / GEO。

3. **英文投入程度**
   推荐中文为主、英文保留最低完整入口。等出现真实英文用户或英文搜索流量，再投入完整英文文档。
